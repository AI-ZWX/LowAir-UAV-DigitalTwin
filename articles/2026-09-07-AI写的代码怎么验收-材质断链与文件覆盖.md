# AI 写的代码，怎么验收：从材质断链到一天九次崩溃

## 先说结论

团队里开始用 AI 写代码之后，我发现真正的风险不是"AI 写得对不对"——写得不对可以改——而是**没有任何机制告诉你：它写的东西，真的生效了吗**。这个问题一年内让我付出四次事故的代价，最后逼出了一套三层防护。

如果你也在用 AI 辅助开发，尤其是 UE 这类"改了还得编译、编译了还得重载"的重型工程，这篇里的每个坑你可能都会遇到。我把四次事故按断掉的环节讲清楚，希望你能一个都别踩。

## 案例一：围栏在 Lit 渲染下消失（9/5）——资产被静默改坏

9 月 5 日，一件很小的事：给电子围栏加边缘发光，让 M_FenceYellow 和 M_FenceRed 在场景里更醒目。这类实现活儿在我这个项目里固定是人提目标、AI 写脚本。脚本做了三件事：材质改 UNLIT、加 Fresnel、加 EdgeBoost。

跑完一切正常——日志里 `ShadingModel=0 (UNLIT)` 明明白白，材质文件也落盘了。直到打开 PIE：

Unlit 视口下，围栏 A 是紫的，B 是青的，地标光柱好好立着，一切正常。**切换到 Lit 游戏渲染，围栏没了。**不是变黑，是全透明，像这两个对象从来没被创建过。

排查三步。第一步就排除了最像答案的答案：日志白纸黑字，UNLIT 生效了。第二步查颜色接没接上：用 `get_material_property_input_node` 看 Emissive 的输入端——返回 NONE，悬空的。输出端没接任何东西，UNLIT 材质的发光值就是 0，等于全透明；Lit 下既没有正常光照链路，自发光又是零，什么都不剩。"消失"解释通了。

第三步，才是这个坑真正的形状。回读 AI 的脚本：加 Fresnel 需要把原来的 Emissive 链拆开、插进新节点、再重新连回去，用的 API 是 `connect_material_expressions`。我把这一步单独拎出来测——**这个 API 在我的环境里每一次调用都返回 False**。它不抛异常、不警告、不写日志，安安静静返回一个 False。等我发现的时候，材质已经"改完"了。

还有个旁证：另一个材质 M_SceneDarken，四条连接全部返回 False。这不是脚本哪一步写错了，是这类 API 在这个环境里就是不可靠。

事故链拼起来是这样的：

```
AI 脚本拆开了原 Emissive 链
→ 重连 API 返回 False（没人知道）
→ 链断着，输出悬空 = 0
→ UNLIT 发光值 = 0
→ 围栏全透明 → "消失"
```

修复只能手动：回滚 Fresnel 修改，在编辑器里把原始 Emissive 直连链恢复出来，UNLIT 保留。这里有个 UE 工程特有的痛——`.uasset` 不进 git，没有 `git checkout` 可以救命，改坏了没有后悔药，只能一行行核对。第二天（09-06）确认恢复。

这一案留下的教训只有一句话：**"没报错"和"成功了"之间，隔着一个打印返回值的距离。**

## 案例二：一个文件被覆盖，一天崩溃九次（9/7）——代码被整个换掉

9 月 7 日，项目 P0 收尾，改动最密的一天。凌晨 0:09 第一次崩溃，到下午 14:35，第 9 次。形态一模一样：空指针写入。那天的节奏是：崩了，重启，改，再崩。这个循环我跑了一整天——现在回头看，**把重启当修复，本质是赌"这次会不一样"**，连续赌了八次。

晚上终于停下来认真查。所有崩溃指向同一片区域，最后锁定 `AlertHUDManager.cpp`。疑点很朴素：这个文件的大小和 AlertTimelineWidget.cpp 一模一样——16822 字节。打开看，内容也一模一样。

**一个源文件的内容，被整个覆盖成了另一个文件。**

项目指令里有明确记录：动手的是 AI——前一晚 19:58，AI 最后一次"修改" AlertHUDManager.cpp，那次写入就是把别的文件的内容写了进去。编辑器一直开着，Live Coding 热重载试图编译这个内容完全错乱的编译单元，编译失败，引擎加载了损坏的二进制——空指针写入，崩溃。编辑器只要开着就会反复触发，一天 9 次。

修复本身不复杂：`git show HEAD` 把原始内容捞回来，重新打上本来要做的修改，清理掉根目录攒下的 40 多个诊断脚本。崩溃停了。

但这一天我真正学到的不是这个：9 次崩溃里有 8 次本来可以避免——第 3 次同形态崩溃出现的时候，我还在重启循环里，没有停下来找共性。AI 覆盖了文件，可拿重启当修复，是我的失误，这部分跟 AI 无关。

## 案例三：改了没生效，一年内还有两次（8/23、9/8）——编译链悄无声息地过期

单看 9/7，像一次孤立的 AI 失误。把它和前后两起摆在一起，模式就清楚了——**三次事故，同一个根因的三个形态**：

**8/23，改了，没编进去。** 无人机颜色修复合入后，重启运行还是旧颜色。代码逻辑对、材质资产对、参数链路对，现象就是不变。这种"每个环节都正常但结果不变"的问题最耗人——你查的每一条路都回报"没问题"，信心一点点被磨掉。查到下午才在二进制层找到突破口：DLL 的编译时间 11:59:38，**早于**所有源码修改（13:59、13:19）。新代码从来没进过二进制。中间还有个差点带偏方向的现象：我用 MCP Python 直接改运行时材质参数，颜色立刻变了，几秒后又被旧逻辑覆盖回去。当时这看起来很像"资产有问题"，现在回头看，它恰恰证明跑的是旧代码。

**9/8，编了，没重载。** 围栏虚线和地标光柱悬在空中，离地 64.3 米。第一反应是高程数据错了——我用运行时工具实测坐标转换函数：期望 15.5m 的位置，函数给出 15.49m，转换是对的；再读 Actor 实际位置：79.8m；查时间戳：源码改到 17:11，DLL 停在 13:13。**又是旧二进制。**停 PIE、编译、重启，围栏落回 15.5m，前后 20 分钟。

这两次还有一个共性值得单独说：**现象都完美伪装成了数据问题**——旧颜色、悬空 64 米。如果按现象去修数据，会永远修不好，还会把好的数据改坏。

## 根因：四个环节，缺的是同一个东西

四个案例断了四个环节：资产可能被静默改坏（案例一）、文件可能被覆盖（案例二）、改了可能没编译（8/23）、编译了 PIE 可能没重载（9/8）。共同点是：**整个工作流里没有任何机制保证"运行的代码 = 你以为正在运行的代码"，每个环节都靠自觉。**

一个人加一个 AI 帮手、高频改动的场景里，自觉是靠不住的：AI 会写错文件，API 会静默失败，人会拿重启当修复。

## 怎么修的：三层防护，每层对着一种事故形态

9 月 21 日起，三层防护全部在岗：

1. **写盘前校验**——`Protect-L4SourceWrite.ps1`：改 `Source/` 或 `Content/` 任何文件之前先跑，校验文件内容跟它的身份一致，退出码非 0 禁止写盘。对着案例二这种"AI 写错文件"。
2. **pre-commit 钩子**——提交前再拦一道。
3. **WriteGuard**——编辑器侧保护。

外加两条纪律：**改完不编译不验，等于没改；AI 说"改完了"，验收动作不能省。**

## 下回怎么做（checklist，可直接拿走）

- [ ] 返回布尔的 API，一律打印返回值复核——"没报错"不算数
- [ ] Python 不改材质节点（不管脚本谁写）；改材质前留原状，uasset 不进 git，改坏了无法回滚
- [ ] 写盘前跑校验脚本，退出码非 0 立即停手——对 AI 的写盘和人的写盘一视同仁
- [ ] "行为不对 / 位置不对"类问题，第一动作是核对 `Binaries/Win64/*.dll` 时间戳 vs 源码修改时间，确认跑的是新代码，再开始怀疑数据
- [ ] Live Coding 编译成功后必须重启 PIE，旧会话不会自动应用补丁
- [ ] 用实测对位排查，不用猜：调一次转换函数看输出，对比实际值，30 秒分清"算错了"还是"没生效"
- [ ] 同形态崩溃 ≥3 次，停止重启循环，先找共性再动手
- [ ] AI 产出的修改，验收标准和人写的一样高——信任不豁免验证

## 写在后面

每处理完一起这类事故，我都会把完整过程记进台账：时间线、每一个"我以为"、最终的对照数据。这份记录最大的作用不是给谁看，而是留给下一次踩坑的自己——这个项目已经证明了一件事：**没有复盘的事故，会换一种形态再来一次。**

回头看，四次事故里三次本可以被几条不值钱的纪律避免：打印返回值、看时间戳、重启前先问自己一句"这次凭什么会不一样"。
