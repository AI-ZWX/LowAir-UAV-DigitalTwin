# AI 写的代码，怎么验收：从材质断链到一天九次崩溃

## 先说结论

**人和 AI 一起写代码，风险不在"AI 会写错"——人也会写错——而在于没有任何机制去确认"写对了、编进去了、跑的是新版本"。** 这个项目一年内为这件事付出四次事故，最后沉淀出一套三层防护。四个案例分别断了四个不同的环节，但缺的是同一个东西。

## 案例一：围栏在 Lit 渲染下消失（9/5，资产层）

给电子围栏做视觉调整，目标很小：M_FenceYellow 和 M_FenceRed 加边缘发光。这类实现工作交给 AI：我提目标，AI 写 Python 脚本。脚本做了三件事：改成 UNLIT、加 Fresnel、加 EdgeBoost。跑完日志里 `ShadingModel=0 (UNLIT)` 明明白白，材质文件也落盘了，看起来一切正常。

开 PIE：Unlit 视口下围栏 A 紫、围栏 B 青绿、光柱正常；切换到 Lit 游戏渲染——围栏不见了。不是变黑，是全透明。

排查分三步：

1. **UNLIT 生效了吗？** 日志白纸黑字，排除。
2. **颜色接上了吗？** 用 `get_material_property_input_node` 查 Emissive 输入端——NONE，悬空的。输出端没接任何东西，UNLIT 材质发光值就是 0，等于全透明。现象解释通了。
3. **链什么时候断的？** 回读脚本：加 Fresnel 需要拆开原 Emissive 链、插节点、再重连，用的是 `connect_material_expressions`。单独测试这个 API——**在我的环境里每一次都返回 False**。它不抛异常、不警告、不写日志，只返回 False；发现的时候材质已经"改完"了。另一个材质 M_SceneDarken 四条连接全部 False，佐证不是脚本写错，是这类 API 在这个环境里不可靠。

修复：回滚 Fresnel 修改，恢复原始 Emissive 直连链，UNLIT 保留。回滚只能手动在编辑器里核对——`.uasset` 不进 git，无法靠版本控制回滚。第二天确认恢复。

## 案例二：一个文件被覆盖，一天崩溃九次（9/7，代码层）

凌晨 0:09 第一次崩溃，到下午 14:35 第 9 次。形态一模一样：`EXCEPTION_ACCESS_VIOLATION` 空指针写入。当时 P0 收尾、改动密集，节奏是：崩了，重启，改，再崩。

晚上停下来认真查，锁定 `AlertHUDManager.cpp`——**它和 AlertTimelineWidget.cpp 大小一模一样：16822 字节，内容也一模一样。** 前一个文件的内容被整个覆盖成了后者。

项目指令里有明确记录：动手的是 AI——前晚 19:58 AI"修改" AlertHUDManager.cpp，那次写入就是把别的文件的内容写了进去。编辑器一直开着，Live Coding 试图编译这个内容错乱的编译单元，失败，引擎加载了损坏的二进制——崩溃，编辑器开着就反复触发。

修复不复杂：`git show HEAD` 捞回原始内容，重新打上本来要做的修改。崩溃停了。

## 案例三：改了没生效，一年内还有两次（8/23 和 9/8，编译链层）

单看 9/7 像一次 AI 失误。把前后两起摆在一起，模式清楚了：

**8/23，改了，没编进去。** 无人机颜色修复合入后，运行还是旧颜色。代码对、资产对、链路对，现象就是不变。查到下午才发现：DLL 编译时间 11:59:38，**早于**所有源码修改（13:59、13:19）——新代码从来没进过二进制。

**9/8，编了，没重载。** 围栏虚线和地标光柱悬空 64.3 米，第一反应是高程数据错了。用运行时工具实测坐标转换函数：期望 15.5m 的位置，函数给出 15.49m——**转换是对的**；再读 Actor 实际位置 79.8m；查时间戳：源码改到 17:11，DLL 停在 13:13。**又是旧二进制。** 停 PIE、编译、重启，围栏落回 15.5m。

这两次的现象都像数据问题。如果按现象去修数据，会永远修不好，还会把数据改错。

## 根因

四个案例断了四个环节：资产可能被静默改坏（案例一）、文件可能被覆盖（案例二）、改了可能没编译（8/23）、编译了 PIE 可能没重载（9/8）。共同点是每个环节都靠"自觉"。一个人加一个 AI 帮手、高频改动的场景里，自觉靠不住：AI 会写错文件，API 会静默失败，人会拿重启当修复。

9 次崩溃里有 8 次可以避免——第 3 次同形态崩溃出现时我还在重启循环，没有停下来找共性。这部分责任在人，跟 AI 无关。

## 怎么修的：三层防护

9 月 21 日起，三层防护全部在岗，每层对应一种事故形态：

1. **写盘前校验**——`Protect-L4SourceWrite.ps1`：改 `Source/` 或 `Content/` 任何文件之前先跑，校验文件内容跟它的身份一致，退出码非 0 禁止写盘。专门防案例二型。
2. **pre-commit 钩子**——提交前再拦一道。
3. **WriteGuard**——编辑器侧保护。

外加两条纪律：改完不编译不验，等于没改；AI 交付任何"改完了"的结论，验收动作不能省。

## 下回怎么做（checklist，可直接拿走）

- [ ] 返回布尔的 API，打印返回值复核，"没报错"不算数
- [ ] Python 不改材质节点（不管脚本谁写）；改材质前留原状，uasset 不进 git 无法回滚
- [ ] 写盘前跑校验脚本，退出码非 0 立即停手——对 AI 的写盘和人的写盘一视同仁
- [ ] "行为不对 / 位置不对"类问题，先核对 `Binaries/Win64/*.dll` 时间戳 vs 源码修改时间，确认跑的是新代码，再怀疑数据
- [ ] Live Coding 编译成功后必须重启 PIE，旧会话不会自动应用补丁
- [ ] 用实测对位排查，不用猜：调一次转换函数看输出，对比实际值，分清"算错了"还是"没生效"
- [ ] 同形态崩溃 ≥3 次，停止重启循环，先找共性再动手
- [ ] AI 产出的修改，验收标准和人写的一样高——信任不豁免验证
